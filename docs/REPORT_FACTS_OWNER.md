# 正規レポートの事実の所有者


ステータス: 内部アーキテクチャ上の決定
記録日: 2026-08-02


## 目的


完全な `ReportBook` は、同じ検証済みの `Journal` をフラット化して、レポートごとに 1 回事実を投稿してはなりません。共有入力は内部値として一度準備され、ポイント残高、期間残高、フロー座標、およびトランザクション全体のレポートに投影されます。


```text
validated Journal
  -> AccountingFacts
       |- canonical LedgerEntry list
       |- AccountRegistry
       `- whole Transaction list
  -> Point / Period / Flow / Recent bases
  -> typed reports
```


`AccountingFacts` は 2 つの異なるセマンティックグレインを保持します。


- 残高とフローの転記粒度 `LedgerEntry` 値。

- 最近のトランザクションの `Transaction` 値全体。


また、宣言されたアカウントの意味の唯一の情報源として、検証された `AccountRegistry` も保持されます。


## 所有


`HKernel.Engine.Facts` は、標準的な事実の準備と事実に基づいた会計クエリを所有しています。


モジュールは内部 Cabal `other-modules` エントリとして登録されます。これは公開されたライブラリ モジュールではありません。


`HKernel.Engine` は公開ファサードのままで、既存のジャーナルベースのクエリ API を公開し続けます。これらの公開機能は、`AccountingFacts` 自体を公開することなく、内部ファクト所有者に委任されます。


レポートの構築では、準備された 1 つの値を複数のレポート ベースで共有する必要があるため、内部所有者をインポートする場合があります。


## 型が内部になった理由


現在の有限の問題は ReportBook のトラバーサル所有権であり、新しいパブリック ライブラリの抽象化ではありません。 `AccountingFacts` を今公開すると、パブリック API を、今後も変更される可能性のある決定に時期尚早にコミットすることになります。


- 情報源の出所が後に標準的事実に属するかどうか。

- トランザクションが直接保存されたままなのか、それとも別の全粒ビューを通じて保存されたままなのか。

- エントリ コレクションがリストのままであるか、型付きインデックスを取得するか。

- 報告事実と一般的な会計照会事実が同じ抽象化のままであるかどうか。


モジュールを内部に保持することで、これらの質問は、事前に推測するのではなく、実際の使用から回答できるようになります。


## パブリック API プロモーション チェックポイント


以下のすべてに該当する場合にのみ、`AccountingFacts` から `HKernel.Engine` を公開することを再検討してください。


1. レポート ライブラリ以外のコンシューマには、一度準備していくつかのクエリを実行するという具体的なニーズがあります。

2. 粒子と保持された座標は複数回の内部使用にわたって安定しているという事実。

3. 抽象化は、現在の ReportBook 構造の便利なラッパーではなく、レポートに中立です。

4. その不変条件、命名、および意図されたクエリの法則は、永続的なライブラリ契約として文書化できます。

5. これを公開すると、単に内部型を到達可能にするだけでなく、ユーザーにとって意味のある繰り返し作業や所有権の重複が削除されます。


そのチェックポイントでは、プロモーションは明示的な API 設計スライスである必要があります。コンストラクターの可視性、アクセサーの表面、互換性の義務、および例をレビューする必要があります。内部モジュールの存在だけでは、それを公開する理由にはなりません。


## 現在の非目標


この所有者は次のことを行いません。


- 考えられるすべての日付または範囲のバランスを事前計算します。

- 変更可能なキャッシュ状態を導入します。

- 会計分類、記号、商品の動作、または期間のセマンティクスを変更する。

- レポート モデル、CLI コマンド、TOML、またはレンダリングを変更します。

- 転記粒度レポートをトランザクション全体レポートに強制する。

- すべてのダウンストリーム投影が 1 回のフォールドのみを実行することを約束します。


現在の減算はより狭く、1 回の ReportBook 実行で正規の投稿リストが 1 回作成されます。点、期間、および流れの投影は、その個別の座標を求めてその共有リストを引き続き横断することができます。さらにクエリとプランを融合するには、別個の証拠とネゴシエーションが必要です。
